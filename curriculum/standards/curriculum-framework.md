# CODEship Academy Curriculum Framework
**Document ID:** CSA-STD-CF-EN-v1.0 · **Status:** Approved for production · **Applies to:** all four programs, all delivery modes (in-person, online, Guyana online)

---

## 1. Purpose

This framework is the pedagogical constitution of CODEship Academy. It records the educational philosophy, program architecture, session model, assessment model, and inclusion standards that every program volume implements. Nothing in a program manual may contradict this framework; anything repeated across programs is defined once, here.

## 2. Educational philosophy

CODEship's mission: **help every child discover their capacity to create — using digital tools as a medium for imagination, problem-solving, and self-expression.**

Core beliefs (verbatim brand commitments, used across all public materials):

1. Every child has ideas worth building.
2. Creativity comes before code.
3. Real projects build real confidence.
4. Technology belongs to everyone.
5. Learning happens best through making.
6. Community and school are where access begins.

Operating principle: **Creativity Before Code.** Children bring ideas; CODEship provides tools, structure, and encouragement. Students do not follow tutorials or fill in templates — every project is genuinely theirs, built from a shared brief that each student makes their own.

## 3. Program architecture — the CODEship Journey

Four connected levels take a child from Kindergarten to Grade 8:

| Level | Grades | Coding space | Journey arc | Headline outcome |
|-------|--------|--------------|-------------|------------------|
| Explorers | K–1 | Visual block coding | Dream | Gives a computer clear instructions and builds a simple interactive app. |
| Builders | 2–3 | HTML & CSS | Dream | Builds and styles a real multi-page website. |
| Developers | 4–5 | JavaScript | Code | Builds interactive tools that solve real problems. |
| Engineers | 6–8 | Python + AI + Cybersecurity | Achieve | Codes in Python, trains an AI responsibly, and pitches a real tech solution. |

**Structure of every program (public commitment):** 4 semesters + a capstone, ~20 sessions, 8 quizzes (2 per semester), project-based, with inclusive-design accommodations built in.

**Canonical delivery structure (v1.0):**

- Each semester = **5 sessions** (S x.1 – x.5), one project per semester.
- Capstone = **2 additional sessions** (C.1, C.2) after Semester 4, ending in a showcase. Total: 20 semester sessions + capstone, matching the public "~20 sessions total, plus a capstone project".
- Every session = **55 minutes** (both in-person Saturday classes and online weekday classes).
- Quizzes land in sessions **x.3** (mid-semester) and **x.5** (end of semester): Q1–Q8 across the program.

No prior coding experience is required at any level; every semester's first session re-establishes fundamentals before advancing.

## 4. The session model

Every session follows the same four-phase flow (a public commitment on every program page):

| Phase | Minutes | What happens |
|-------|---------|--------------|
| **Warm-up** | 5 | A quick activity that reviews last session's ideas and gets everyone thinking in code. (Retrieval practice.) |
| **Teach** | 10 | Instructor introduces the session's concept through a short, hands-on demonstration. (Direct instruction, worked example.) |
| **Build** | 30 | The bulk of class time — students apply the concept to their own project with instructor support. (Project-based learning.) |
| **Reflect** | 10 | Students share progress, get warm feedback, and set a goal for next session. (Metacognition, formative assessment.) |

**Quiz sessions (x.3 and x.5):** the first 10 minutes become the knowledge check (replacing Warm-up and half of Teach); Teach shrinks to a 5-minute re-teach of whatever the quiz revealed as shaky.

## 5. Assessment model

Assessment at CODEship is frequent, low-stakes, and growth-oriented. Three public commitments define it:

1. **2 quizzes per semester (8 total)** check understanding of key concepts along the way.
2. **A project rubric** evaluates each semester's build — *not just whether it works, but the thinking behind it.*
3. **Warm, specific feedback** from instructors after every project, focused on growth and encouragement.

Implementation standards:

- **Diagnostic:** a no-grade "first voyage" activity in session 1.1 of each program establishes a baseline (see each Assessment Manual).
- **Quizzes:** 5 questions, 10 minutes, formats age-adjusted (circle-the-picture for Explorers through short-answer and code-reading for Engineers). Results are never posted or ranked; they feed the instructor's re-teach and the parent update.
- **Rubrics:** 4 levels — Emerging, Developing, Proficient, Extending — across 4 criteria: *Concept & creativity*, *Technical skill*, *Process & problem-solving*, *Communication & sharing*. Program rubrics adapt the descriptors, never the structure.
- **Self- and peer-assessment:** every project ends with a student self-reflection (workbook) and a structured "warm feedback" peer exchange: one specific compliment ("I like…"), one curiosity ("I wonder…"), delivered orally for K–3 and in writing for 4–8.
- **Reporting:** after each semester project, parents receive rubric results plus two or three sentences of warm, specific instructor feedback (see Parent Handbooks).

## 6. Research-based practices embedded in every program

| Practice | Where it lives in the model |
|----------|------------------------------|
| Computational thinking | Explicit strand at every level: decomposition, sequencing, patterns, abstraction, debugging |
| Project-based learning | One real project per semester; capstone from the student's own idea |
| Inquiry-based learning | Each semester opens with a driving question (the "Big Idea") |
| Universal Design for Learning | Multiple means of engagement/representation/expression; see §7 |
| Formative assessment | Quizzes as checkpoints, Reflect phase every session |
| Retrieval practice | Warm-up phase every session |
| Metacognition | Reflection pages in every workbook; goal-setting in Reflect |
| Growth mindset | "Warm, specific feedback focused on growth"; debugging framed as normal, expected, and interesting |
| Collaborative learning | Peer feedback protocol; pair activities; showcase events |
| AI literacy | Age-appropriate strand: from "computers follow instructions" (K–1) to training, evaluating, and auditing models for bias (6–8) |
| Digital citizenship | Explicit strand: kindness online and digital footprint (K–3), media literacy (4–5), cybersecurity, privacy, and responsible AI (6–8) |
| Cross-curricular integration | Writing (Builders), media & financial literacy (Developers), data/mathematics and ethics (Engineers) |
| Executive function | Goal trackers, progress trackers, planning sheets, predictable session structure, visual schedules |
| Entrepreneurship & communication | Presentation moments every semester; Engineers capstone is a pitched prototype addressing a UN Sustainable Development Goal |

## 7. Inclusion and differentiation (non-negotiable standard)

Inclusive-design accommodations are **built into every class** — a public promise on every program page. Minimum standard in every session plan:

- **Flexible pacing:** every Build phase defines a core task plus a "lighter load" variant and a "stretch" extension; nobody is ever "behind".
- **Multiple ways to show understanding:** speak it, draw it, build it, or write it — rubric evidence may come in any of these forms.
- **Support structures:** visual schedules posted every class; instructions given orally *and* visually; pair support available; movement breaks permissible at any age.
- **Individual accommodations:** families are invited to flag specific needs before the first session; instructors receive them via the class roster and the Classroom Operations Manual protocol (→ CSA-STD-OPS-EN §6).
- **Design accessibility:** materials photocopy-safe in black and white; colour never carries sole meaning; fonts and layouts follow the publishing standards' readability rules.

## 9. Curriculum alignment posture

Alignment claims are made program-by-program and always as "designed to support / maps to / aligns with":

- **Explorers:** Ontario early digital literacy expectations; foundational strand of BC's ADST.
- **Builders:** Ontario coding expectations; BC ADST; Alberta primary Computer Science outcomes.
- **Developers:** Ontario coding and financial literacy expectations; Alberta Computer Science and CTF outcomes.
- **Engineers:** Ontario coding and AI literacy expectations; Alberta Computer Science and CTF; Québec's Cadre de référence de la compétence numérique (offered in French — see STD-FR).

Mandatory disclaimer wherever alignment appears: *Not endorsed or approved by any ministry of education.*

## 10. Software and platform posture

CODEship's curriculum is **platform-flexible by design**: manuals specify the *category* of tool and the skills it must support, with a recommended default, so franchises are never blocked by a single vendor.

| Program | Tool category | Recommended default |
|---------|---------------|---------------------|
| Explorers | Tablet/desktop visual block-coding environment for pre-readers | ScratchJr (tablet) or equivalent |
| Builders | Browser-based HTML/CSS editor with live preview | Any kid-safe web editor with split code/preview view |
| Developers | Browser-based HTML/JS playground with console | Same editor family as Builders, with JS enabled |
| Engineers | Browser-based Python environment + no-code ML trainer + spreadsheet/CSV tools | Browser Python (e.g., replit-style or Trinket-style) + Teachable-Machine-style trainer |

Franchise locations may substitute equivalents only if every skill in the program's skills matrix remains teachable (→ CSA-STD-FDS-EN §4).
